# HNSW 向量索引设计

> 状态：P1–P5 全部实现；后续演进见第 10 节
> 分支：`feat/hnsw-ann-index`
> 适用代码：`src/vector/hnsw_index.{h,cpp}`、`tests/test_hnsw_index.cpp`

本文记录 MinKV 引入 HNSW 近似最近邻索引的设计取舍、实测数据、已经踩过的坑，
以及后续阶段的验收标准。文档里的数字都是在本机（4 vCPU 虚拟机、`g++ 13.3`、
`-O2 -march=native -mavx2 -mfma`、单线程）实测得到的，不是估算。

---

## 1. 问题

当前 `ShardedCache::vectorSearch`（`src/core/sharded_cache.h`）是暴力检索：

1. 每个分片起一个 `std::async`（默认 32 分片就是每查询 32 个线程）；
2. 每个线程 `shard->get_all()` 做一次全量 `std::map` 拷贝；
3. 每条向量再 `VectorOps::DeserializeCopy` 拷贝一次；
4. `L2DistanceSquare` 算距离，局部 Top-K 堆，最后合并。

复杂度 O(N·D)，外加每查询与分片数同量的线程创建和三份数据拷贝。

### 1.1 暴力基线（实测）

top_k = 10，单线程，32 分片，走的就是上面这条真实路径：

| N | dim | P50 | P95 | P99 | 吞吐 |
|---|---|---|---|---|---|
| 1,000 | 768 | 1.920 ms | 4.440 ms | 12.157 ms | 410 QPS |
| 10,000 | 768 | 7.728 ms | 10.553 ms | 15.840 ms | 121 QPS |
| 100,000 | 128 | 35.501 ms | 40.306 ms | 68.937 ms | 26 QPS |
| 100,000 | 768 | 93.186 ms | 121.421 ms | 121.421 ms | 9.6 QPS |

两个观察：

- **小规模下固定开销占主导**。1,000 × 768d 的纯计算只有约 0.06 ms，实测 1.92 ms，
  剩下 1.86 ms 是每个分片一次线程创建 + 一次 map 拷贝。HNSW 在小规模上的收益不是
  「算得快」，而是这些开销整体消失。
- **容量淘汰真实发生**。10 万条写进 32 分片（每片 3141 容量）后只剩 99,504 条，
  哈希分布不均导致 496 条被 LRU 挤掉。这直接决定了索引必须处理淘汰，见第 5 节。

### 1.2 一份过期的性能报告

`docs/SEARCH_PERFORMANCE_REPORT.md` 声称 10K/768d 的 P99 是 81 ms，实测只有 15.8 ms，
差 5 倍。该报告引用的 `vector_search.h` 已经不在仓库里了。**不要拿它作基线或验收依据。**

## 2. 目标与非目标

目标：

- 100K × 128d、top_k = 10 的 P99 从 69 ms 降到 5 ms 以内；
- recall@10 ≥ 0.95（真实 embedding 分布）；
- 不改变既有 `/vector/search` 的**默认**语义与响应结构（向后兼容 MCP 客户端）；
- 近似结果必须可识别，并能退回精确检索。

非目标（本阶段不做）：

- 索引持久化与启动加载（降级为启动重建）；
- 量化（PQ/SQ）；
- 多度量共图。

## 3. 总体设计

```
  HTTP /vector/search        GraphStore::SearchSimilarNodes
            |                          |
            +-----------+--------------+
                        |
                 ShardedCache
        （持有两个独立索引实例，共享同一套算法）
                        |
        +---------------+----------------+
        |                                |
  VectorAnnIndex (L2)            VectorAnnIndex (cosine)
  key <-> uint32, 锁, 统计        仅索引 "vec:" 前缀
        |                                |
        +---------------+----------------+
                        |
                    HnswIndex
        （纯算法：分层图、启发式选邻、Tombstone）
```

### 3.1 一套算法，两套实例

`HnswIndex` 不含任何 KV / 字符串 / 锁的概念，只认 `uint32_t` 内部 id 和 `float` 向量。
`VectorAnnIndex` 负责 key 映射、并发控制、Tombstone 压缩策略。

两个业务各自要一种度量，但**不复制算法**：

| 实例 | 度量 | 收录范围 | 服务的业务 |
|---|---|---|---|
| L2 索引 | 平方欧氏距离 | 所有满足 `size == dim*4` 的 KV 值 | `/vector/search`（保持现有排序语义） |
| Cosine 索引 | 1 - 余弦相似度 | 仅 `vec:` 前缀（图节点 embedding） | `GraphStore::SearchSimilarNodes` / GraphRAG |

### 3.2 为什么不是「全局统一 cosine」

对单位向量 x、y 有 `||x-y||² = 2(1 - cos(x,y))`，此时平方 L2 与余弦同序。
但 MinKV 的 `vectorSearch` 接收的是调用方直接传进来的浮点数组，
**没有任何地方保证它们已归一化**，因此这个等价关系不成立。
为了省一张图去改变公共接口的排序语义，不划算。

同一个理由也要求一个索引实例只认一种度量：分层的贪心下降依赖
「距离沿边单调下降」，换度量查询会让这个假设失效。

### 3.3 几个必须写死的口径

- **`vec:` 的向量必须同时留在 L2 索引里。** 现有 `vectorSearch` 是按
  `raw.size() == query.size()` 匹配的，`GraphStore::SetNodeEmbedding` 写入的
  `vec:` 原始 float 也会被 `/vector/search` 返回。把 `vec:` 从 L2 索引排除会改变
  现有响应，和「保持兼容」直接冲突。代价是这批向量被两份索引各存一份，属于有意为之。
- **L2 侧只索引一个配置维度，其余维度回退精确路径。** 当前存储允许混合维度
  （`vectorSearch` 是逐条比较长度的），实现上曾考虑「每个维度一个实例」，
  但那会让 `enable_ann_index` 的语义变得含糊。最终选择：只为一个维度建索引，
  查询维度不匹配时**明确回退到暴力扫描**（`vectorSearchScored` 内部判断）。
  代价是那个维度没有被加速，好处是绝不会静默漏结果。需要加速第二个维度时，
  再调用一次 `enable_ann_index`（P4 之后支持）或为它单独建一个 ShardedCache。
- **余弦侧可以是单维度**（图节点通常来自同一个 embedding 模型），但维度不符时
  必须显式报错，而不是悄悄跳过。

### 3.4 向量判定：`size == dim*4` 是过渡方案

用字节长度判断「这是不是一个向量」只能保证与现有行为一致，无法证明语义。
这也意味着等长的随机 blob 会被当成向量。长期应改为显式向量类型或命名空间约定，
在 P4 之后单独排期，不在本次改动里顺手做。

## 4. HnswIndex（P1，已实现）

### 4.1 接口

```cpp
enum class AnnMetric { L2, COSINE };

struct HnswConfig {
  size_t dim = 0;                // 必须 > 0
  size_t M = 16;                 // 非零层邻居上限
  size_t M0 = 32;                // 第 0 层邻居上限
  size_t ef_construction = 200;
  AnnMetric metric = AnnMetric::L2;
  uint64_t seed = ...;           // 层级抽样种子，固定可复现
};

class HnswIndex {
  uint32_t insert(const float* vec);                    // 追加式，id 单调不复用
  bool erase(uint32_t id);                              // 只打 Tombstone
  std::vector<AnnHit> knn(const float* q, size_t k, size_t ef) const;
  void compact();                                       // 原地重建图，id 不变
  size_t reachable_count() const;                       // 图健康体检
};
```

约定：

- `AnnHit::score` 统一表示**距离**，越小越近。L2 返回平方距离（省 sqrt 且保序），
  余弦返回 `1 - similarity`，需要相似度就 `1 - score`。
- `insert` / `erase` / `compact` **不加锁**，并发由上层负责。

### 4.2 算法要点

- 层级抽样：`floor(-ln(u) / ln(M))`，`u` 来自 splitmix64，同 seed 完全复现。
- 插入：从入口贪心下降到目标层以上，再逐层 `search_layer(ef_construction)`
  → 启发式选邻（论文 Algorithm 4）→ 双向连边 → 超容量裁剪。
- 搜索：贪心下降到第 0 层，`search_layer(max(ef, k))`，跳过 Tombstone，取前 k。
- 访问标记用「线程局部时间戳数组」而不是每次查询 `memset` 一个 N 字节的数组，
  否则 10 万节点每次查询要多扫 100 KB。

### 4.3 内存布局（P2.5 之后）

第 0 层单独用「定长平铺 + 原子计数」：每节点固定 `M0` 个槽位，
`l0_slots_[node * M0 + i]` 是 `std::atomic<uint32_t>`，`l0_counts_[node]` 记录当前邻居数。
写侧只在尾部追加，然后 release 发布计数；读侧 acquire 读计数后逐槽 relaxed 读取。
好处有三：读路径无需加锁、realloc 不会造成悬空读、省掉每跳一次的指针追逐。

第 1 层及以上节点只占约 `1/M`，仍用 per-node vector，进入这些层时临时持节点锁复制一份。
实测 100K × 128d 的索引内存从 83 MB 降到 65 MB。

## 5. 一致性设计（P3）

### 5.1 所有删除路径都汇到一处

`ShardedCache` 里向量被拿走的方式有四种：显式 `remove`、TTL 过期、
容量淘汰、`clear`。前三种最终都调用 `LruCache::erase_node`（`src/core/lru_cache.h`）。
但 `LruCache::put` 的淘汰分支只 `++stats_evictions_`，**不告诉任何人淘汰了哪个 key**。

因此 P3 的最小改动是给 `LruCache` 加一个回调：

```cpp
void set_on_erase(std::function<void(const K&)> cb);
// erase_node 内、真正 erase 之前调用
```

一处挂上，同时覆盖显式删除、TTL 过期与容量淘汰。

### 5.2 需要同步索引的位置

| 位置 | 动作 |
|---|---|
| `vectorPut` | `ann.upsert` |
| `put` | `value.size() == dim*4` → upsert，否则 erase（同一 key 可能被改写成标量） |
| `remove` | `ann.erase` |
| `update_in_place` | RMW 完成后按同一规则重索引 |
| `clear` | `ann.clear()` |
| `put_for_recovery` / `remove_for_recovery` | 同 put / remove |
| `LruCache::erase_node` | 回调 → `ann.erase_if_exists` |

### 5.3 锁序与死锁

**只允许 `shard → ann`，绝不允许 `ann → shard`。**

因为淘汰回调是在分片锁内触发的（`erase_node` 由 `put` / `expire_keys` 调用），
它需要拿索引的写锁。如果搜索路径在持有索引锁的情况下去回查缓存（`cache->get`），
就会形成反向等待，必然死锁。

所以 `vectorSearch` 必须是：**在 ann 的共享锁内收集结果 → 释放锁 → 再回缓存校验存在性**。
校验这一步是为了对抗「索引与缓存之间的短暂不一致窗口」（写入 KV 成功、索引尚未更新）。

### 5.4 无法完全消除的窗口

`put(key)` 成功到 `ann.upsert(key)` 完成之间，索引里没有这个 key。
在此期间并发查询可能看不到这条向量，或看到旧向量的邻居关系。
这是「先落 KV 再更新索引」模型的固有代价，可接受，但要在文档和测试里写明：
**ANN 结果是最终一致的，不是线性一致的。**

反方向的窗口（索引里还有、缓存里已经没了）用一次锁外回查兜住：
`vectorSearchScored` 拿到 ANN 结果后释放索引锁，再对每个候选调用
`shard->contains(key)`，已淘汰的 key 直接被过滤掉。

### 5.5 实现要点（P3）

| 位置 | 做法 |
|---|---|
| `LruCache::erase_node` | 新增 `on_erase_` 回调，在真正摘链之前调用；一处覆盖 remove / TTL / 淘汰 |
| `ShardedCache` 构造 | 给每个分片挂 `set_on_erase([this](k){ ann_on_erase(k); })` |
| `put` | 分片写入返回后调用 `ann_on_put`（分片锁已释放） |
| `update_in_place` | 改为先取回新值再 `ann_on_put`，否则向量被 RMW 改写后索引仍是旧值 |
| `clear` | `ann_on_clear()` |
| `vectorSearchScored` | ANN 结果 → 释放锁 → `contains` 回查 → 返回 |

三条实现上的硬约束：

1. **回调里绝不 compact。** `ann_on_erase` 是在分片锁内被调用的，
   整图重建会把分片卡住几百毫秒。因此新增了
   `VectorAnnIndex::erase_without_compaction`，压缩统一交给显式路径。
2. **回调必须幂等。** 淘汰与 `remove` 可能对同一个 key 各触发一次，
   索引侧的 erase 对「不在映射里」的 key 直接返回 false。
3. **写路径有一个恒定开销**：`ann_on_put` 对每次 put 都要判断
   `value.size() == dim * 4`，不匹配时还要把该 key 从索引里撤下
   （key 从向量被改写成了标量）。开启索引后普通 KV 写入会多两次哈希查找，
   这是「用字节长度判断是不是向量」这一妥协的连带成本，见 3.4。

### 5.6 对外接口（P4）

`POST /vector/search` 新增可选字段 `exact`（强制精确扫描）与 `ef`（覆盖搜索宽度）；
响应在保持 `results` 为 **key 字符串数组**的前提下，新增 `scores`（与 results 平行的
距离数组）、`search_mode`（`ann` | `brute`）、`latency_us`。
保持 `results` 的类型不变是刻意的：`mcp_server/` 的 Python 客户端按字符串数组解析，
改成对象数组会直接打断它。

GraphRAG 侧：`GraphStore::SearchSimilarNodes` 优先走余弦索引（只含 `vec:` 键），
索引不可用（未启用或维度不符）时回退到原来的全量扫描，签名与返回语义不变。

顺带补上了缺失的 `examples/http_server_example.cpp`。CMake 里
`http_server_example` 一直由 `if(EXISTS ...)` 保护，而该文件不存在——
也就是说 `src/server/http_server.cpp` 从未被任何 target 编译过，
这也是前面几轮改动「改 HTTP 层却无法验证」的根因。补上之后 HTTP 层才真正进入构建矩阵。

端到端冒烟（dim=4，5 个向量）：

```
POST /vector/search {"query":[0.1,0.2,0.3,0.4],"top_k":3}
  -> results ["v1","v2","v3"]  scores [0, 0.01, 0.04]
     search_mode "ann"  latency_us 32.9
同一请求 + "exact": true
  -> 相同结果  search_mode "brute"  latency_us 24.3
```

## 6. 参数与实测

### 6.0 数字的可信度标注

- **实测**：6.1、6.6 的全部表格，由 `tests/benchmark_hnsw.cpp` 一条命令复现。
- **目标**：第 2 节的验收线（P99 < 5 ms、recall ≥ 0.95）是设计目标，不是结论；
  其中 P99 在聚类数据上大幅达标，召回率则完全取决于数据分布，见 6.3。
- **估算**：6.2 的两行来自 `HnswIndex` 直测（不含 ShardedCache 的分片与回查开销），
  只用于说明参数档位，不要与 6.1 直接相减。

另有一条测量纪律：同一配置的精确基线在三次独立运行里分别是 57.8 / 87.2 / 61.9 ms
（P99 62 / 126 / 104 ms），差异来自机器负载与内存状态。
**跨运行的绝对加速比不可比，只在同一次运行内做比值。**

### 6.1 默认档（RAG 场景）

`M=16, M0=32, ef_construction=200, ef=64`，4 线程建图，k=10，20 条查询。
全部由 `tests/benchmark_hnsw.cpp` 生成，一条命令可复现（见文末附录）。

| 数据集 | N | dim | build | 精确 P50 / P99 | ANN P50 / P99 | 加速 | recall@10 |
|---|---|---|---|---|---|---|---|
| 聚类 | 20,000 | 128 | 1.9 s | 9.11 / 10.55 ms | 0.096 / 0.127 ms | 95× | 1.0000 |
| 聚类 | 100,000 | 128 | 12.0 s | 61.27 / 64.83 ms | 0.210 / 0.297 ms | 291× | 1.0000 |
| 聚类 | 10,000 | 768 | 3.0 s | 10.97 / 11.49 ms | 0.212 / 0.429 ms | 52× | 1.0000 |
| 均匀 | 20,000 | 128 | 4.1 s | 9.22 / 10.79 ms | 0.363 / 0.405 ms | 25× | 0.6500 |
| 均匀 | 100,000 | 128 | 40.5 s | 57.88 / 61.26 ms | 0.539 / 1.933 ms | 107× | 0.3800 |

两点读法：

- 「加速」列是 **P50 之比**。同一行按 **P99** 算是 218×（64.83 → 0.297 ms），
  不是 291×。对外表述必须写清是哪一档，不要把 P50 的倍数说成尾延迟提升。
- 「精确」列比 1.1 的基线慢约 40%（100K/128d 从 35.5 ms 到 61.3 ms），因为基准程序
  按生产路径构造 32 分片缓存并在同进程里持有索引，内存压力更大。
  两列出自同一个二进制、同一次运行，**横向比较才有效**，不要跨表比绝对值。
- 均匀数据上的 0.38 不是索引的问题，见 6.5 与 6.3。

内存：100K × 128d 索引 64.7 MB（向量数据本身 51 MB，约 2.3×），10K × 768d 30.9 MB。
100K 那两行的 `live` 是 99,885 —— 分片哈希不均挤掉了 115 条，与 1.1 的观察一致。

### 6.3 ef 扫描：达到目标召回要付多少延迟

这是整个项目里最该被问到的一张表。同一批 20 条查询、k=10、M=16，
`dist/query` 由 `-DHNSW_TRACE_DISTANCE` 计数得出：

```bash
cmake -S . -B build/trace -DCMAKE_BUILD_TYPE=Release -DHNSW_TRACE_DISTANCE=ON
cmake --build build/trace --target benchmark_hnsw -j2
./build/trace/bin/benchmark_hnsw sweep uniform 100000 128 16 64,128,256,512,1024,2048
```

**聚类 100K × 128d**（真实分布，建图 14.4 s）

| ef | recall@10 | P50 | P99 | 距离计算/查询 | P50 加速 | P99 加速 |
|---|---|---|---|---|---|---|
| 32 | 0.9950 | 0.096 ms | 0.144 ms | 26 | 659× | 470× |
| 64 | 1.0000 | 0.131 ms | 0.159 ms | 29 | 484× | 427× |
| 128 | 1.0000 | 0.170 ms | 1.093 ms | 31 | 373× | 62× |

聚类数据只要约 30 次距离计算就够了，默认 `ef=64` 偏保守；`ef=32` 已经有 0.995。

**均匀 100K × 128d**（对抗性分布，建图约 40 s）

| ef | recall@10 | P50 | P99 | 距离计算/查询 | P50 加速 | P99 加速 |
|---|---|---|---|---|---|---|
| 64 | 0.370 | 0.301 ms | 0.488 ms | 116 | 206× | 213× |
| 128 | 0.565 | 0.551 ms | 1.866 ms | 187 | 105× | 33× |
| 256 | 0.715 | 1.009 ms | 3.004 ms | 353 | 57× | 21× |
| 512 | 0.860 | 1.910 ms | 4.078 ms | 619 | 30× | 15× |
| 1024 | 0.915 | 3.559 ms | 5.713 ms | 1045 | 17× | 18× |
| 2048 | **0.970** | 5.928 ms | 8.052 ms | 1652 | 10× | 13× |

三条结论：

1. **要在这类数据上做到 0.95+ 召回，需要把 ef 从 64 提到 2048（32 倍）**：
   延迟从 0.30 ms 涨到 5.93 ms，加速比从约 200× 掉到约 10×。
   仍然比暴力快一个数量级，但「291×」绝不能当作通用承诺。
2. **召回率不能靠固定 ef 保证。** 同一份代码、同样 `ef=64`，聚类数据 1.000、
   均匀数据 0.370。上线前必须用目标数据的一段样本实测「ef — 召回」曲线，
   再按可接受的延迟选 ef。
3. **距离计算次数是唯一稳定的解释变量。** 召回从 0.370 涨到 0.970，
   对应 `dist/query` 从 116 涨到 1652；128d 下每增加一条平均约 3.5 µs，
   所以调 ef 的代价几乎严格线性——这比记住某个「加速倍数」更有用。

### 6.4 均匀数据上换 M 有用吗

`M=32, M0=64`（建图 177 s，是 M=16 的 3.7 倍）：

| M | ef | recall@10 | P50 | dist/query |
|---|---|---|---|---|
| 16 | 512 | 0.860 | 1.910 ms | 619 |
| 32 | 256 | 0.880 | 1.767 ms | 655 |

在 10 万条这个规模上，加大 M 与加大 ef 是等效的：召回接近时距离计算次数也接近，
而 M=32 的建图成本高得多。**所以默认档选 M=16 是对的**；
6.2 里 M=32 能到 0.97 是在 2 万条的小规模上，不能外推到 10 万。

### 6.5 均匀随机 128 维是病态数据

M=16 时 recall 只有 0.65，但**图的连通性是 100%**，聚类数据是 1.000。
说明实现没有问题，是均匀高维本身没有邻域结构：距离高度集中，
「真实 Top-10」之间几乎无区分度。这种情况下任何图索引都会退化。

结论：

- 验收与对外展示**必须用聚类数据或真实 embedding**，均匀随机只能作为压力档；
- 仓库现有的 `comprehensive_benchmark` 里向量那节用的正是均匀随机 128d，
  直接拿它做 A/B 会得出「ANN 不行」的错误结论，benchmark 需要改造；
- 交付前必须把这条写进 `enable_ann_index` 的参数说明。

### 6.6 内存

100K × 128d：向量数据本身 51 MB，索引 83 MB，约 1.6×（原估 2.3×，实测更好）。

### 6.7 建图成本

单次插入 1.3–2.7 ms，绝大多数开销在于「每条反向边都要跑一次 O(m²) 的启发式裁剪」
（32 条反向边 × 33²/2 ≈ 17,000 次距离计算，占单次插入 3 万次计算的一半以上）。

P2.5 的并行建图把墙钟时间压到可以接受（聚类 100K 从 42.7 s 降到 11.9 s），
但单笔插入的成本没变——启动重建依然会吃掉这段时间，只是不再是分钟级。
更进一步的解法是索引落盘或后台构建，属于第 10 节的未决问题。

## 7. 已经踩过的坑

### 7.1 按距离裁剪反向边会把图割裂

第一版 `prune()` 保留「距离最近的 m 个」邻居。稠密簇内部永远有更近的候选，
于是跨簇的桥接边一进列表就被挤掉，整张图碎成若干孤岛。

症状非常特征化：**`ef` 从 64 加到 1024，recall 一点不涨**（0.643 → 0.643），
且部分查询完全零命中。修法是复用建图时的启发式裁剪（论文 Algorithm 4）：

```
聚类 recall@10: 0.643 → 1.000    零命中查询: 8/30 → 0/30
```

诊断手法沉淀成了 `reachable_count()`：从入口在第 0 层做 BFS，
可达数远小于 `size()` 就说明图裂了。这个指标比 recall 更早报警。

### 7.2 `compact()` 不保证提升 recall

Tombstone 节点仍留在图里当导航路标，有时反而比「只留存活节点」的图更容易路由。
实测 40% 删除后 recall 0.9975，compact 之后 0.9950。
所以验收口径是「重建后质量不塌」，不是「重建后必然更好」。

### 7.3 两个并发 bug（只有 TSan + 并发压测能抓到）

**一、`compact()` 换代与并发建图冲突。** 为了不让写操作把检索阻塞一次建图的时长，
`upsert` 把建图放在 `mu_` 之外。但 `compact()` 会在 `mu_` 独占下替换并析构旧索引，
于是仍在旧对象里建图的线程会踩到已释放内存（TSan 报 use-after-free）。
修法：索引用 `shared_ptr` 持有（在用对象不随换代析构），并在发布阶段校验代号——
若期间发生过重建，就在当前代重新插入一次。同理，`erase` 必须与 `ids_` 的摘除
放在同一把锁里，否则跨锁调用时该 id 可能已经属于另一代索引。

**二、`memory_bytes()` 的加锁范围不对。** 它只拿了结构共享锁，却读上层邻接链表的
`capacity()`；那些链表由条带锁保护，会与并发 `add_back_link` 的 `push_back` 撞上。
修法：逐节点按其条带锁读取，且只对 `levels_[node] > 0` 的约 1/16 节点加锁。

两条都属于「锁的粒度选对了、但覆盖范围漏了一块」：单线程测试、召回率测试全绿，
只有 TSan + 并发压测能暴露。

## 8. 并行建图（P2.5，已实现）

### 8.1 目标与结果

| 场景 | 1 线程 | 2 线程 | 4 线程 | 加速比 | recall@10 |
|---|---|---|---|---|---|
| 聚类 100K/128d | 42.7 s | 22.5 s | **11.9 s** | 3.58× | 1.0000 → 1.0000 |
| 均匀 100K/128d | 118.9 s | — | **38.0 s** | 3.13× | 0.320 → 0.300 |
| 均匀 10K/768d | — | — | 8.7 s | — | 0.580 |

- 真实分布（聚类）上**并行构建零召回损失**，图连通性 100%；
- 病态的均匀 128d 上损失约 0.02（并发插入使同期节点之间无法互连，属于该方案的固有代价）；
- 查询侧顺带变快：聚类 100K/128d 的 P50 从 0.118 ms 降到 0.105 ms（定长布局的收益）。

### 8.2 设计

1. **第 0 层邻接表定长平铺**：见 4.3。读侧无锁、无 realloc 风险。
2. **写侧条纹锁**：1024 个 mutex，按 `node & 1023` 取。
   关键约束是**任何时刻只持有一把条带锁**：先写自己的链（锁自己），
   再逐条给邻居加反向边（每次只锁邻居）。因此不存在两把锁的获取顺序问题，
   天然无死锁。
3. **层级序列单线程预生成**：批量构建先一次性抽出全部层数并写好向量槽位，
   再让多线程并发建边。`build_parallel(threads=1)` 因此与逐个 `insert`
   生成**完全相同**的图（测试里逐查询比对 top-k id 验证）。
4. **入口点单独保护**：`entry_point_` / `max_level_` 是原子量 + `entry_mu_`；
   批量构建先单线程链接 0 号节点立好入口，避免并发期间出现孤立节点。
5. **结构锁**：扩容、`erase`、`compact` 取独占；`knn`、`insert` 的建边阶段取共享。
   因此 `insert` 之间可以并发，只有扩容路径会短暂独占。

### 8.3 验收结果（全部通过）

| 验收项 | 目标 | 实测 |
|---|---|---|
| 并行与单线程 recall 差 | ≤ 0.01 | 聚类 **0.0000**；均匀 0.020（病态数据） |
| 4 vCPU 加速比 | ≥ 2.5× | 聚类 **3.58×**，均匀 3.13× |
| 8 线程并发插入 + 并发查询 | 无死锁/崩溃 | 3200 次插入 + 读者线程，通过 |
| `-fsanitize=thread` | 无 race | 干净（需 `setarch -R` 关 ASLR） |

### 8.4 已知代价

- **单线程插入变慢约 19%**（3000 条 48d 数据：751 ms → 894 ms），
  代价来自每次加反向边都要取一次条带锁。批量构建用 `build_parallel` 即可摊平。
- 并发构建的图与顺序构建**不保证逐位一致**（调度影响链接顺序），
  只有 `threads=1` 时才与 `insert` 序列严格一致。
- 病态数据上并行会比单线程低约 0.02 recall，需要在选参时留余量。

### 8.5 TSan 的运行方式

本机内核 ASLR 熵过高，TSan 直接跑会报 `unexpected memory mapping`，
需要关掉 ASLR：

```bash
g++ -std=c++17 -O1 -g -fsanitize=thread -march=native -mavx2 -mfma -pthread -Isrc \
    <stress>.cpp src/vector/hnsw_index.cpp -o /tmp/tsan_stress
setarch $(uname -m) -R /tmp/tsan_stress
```

## 附：数据复现

本文所有表格现在都由 `tests/benchmark_hnsw.cpp` 产出，一条命令即可复现：

```bash
cmake -S . -B build/release -DCMAKE_BUILD_TYPE=Release
cmake --build build/release --target benchmark_hnsw -j2
./build/release/bin/benchmark_hnsw        # 可选参数：k ef 查询条数
```

该程序把精确扫描与 ANN 都跑在 `ShardedCache` 上，因此两列包含同样的分片开销，
ANN 列还包含搜索之后的锁外存在性回查。**不要用 Debug 构建跑它**：
`-O0` 会把两列都放大约 7 倍，比例虽接近但绝对值不可引用。

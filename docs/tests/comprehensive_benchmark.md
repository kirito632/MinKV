# 综合性能测试 (Comprehensive Benchmark)

最后更新：2026-06-18

> 测试意图：验证系统在不同并发度、读写比和命中率下的吞吐量与延迟表现，同时测量 Noop baseline（框架开销）和向量检索性能。
>
> 本次 O2 测试命令：`taskset -c 0-7 ./bin/comprehensive_benchmark`

## 编译

> **注意**：`-mavx2 -mfma` 已在 [`CMakeLists.txt`](../../CMakeLists.txt:13) 中通过 `add_compile_options` 全局添加，编译时无需重复传入。

### O2 编译（默认）
```bash
# 服务器上执行
cd ~/MinKV
mkdir -p build && cd build
cmake -DCMAKE_BUILD_TYPE=Release \
      -DCMAKE_CXX_FLAGS="-O2 -march=native -mavx2 -mfma" ..
make -j$(nproc) comprehensive_benchmark
```

### O3 编译（方案一：推荐，让 CMake Release 模式自动使用 -O3）
```bash
cd ~/MinKV/build
cmake -DCMAKE_BUILD_TYPE=Release ..
make -j$(nproc) comprehensive_benchmark
```

### O3 编译（方案二：显式指定，效果等价）
```bash
cd ~/MinKV/build
cmake -DCMAKE_BUILD_TYPE=Release \
      -DCMAKE_CXX_FLAGS="-O3 -march=native -mavx2 -mfma" ..
make -j$(nproc) comprehensive_benchmark
```

> **说明**：`CMAKE_BUILD_TYPE=Release` 对 GCC/Clang 默认添加 `-O3 -DNDEBUG`。如果同时手动传入 `CMAKE_CXX_FLAGS`，会**覆盖** CMake 的默认 Release 标志，因此 O2 测试需要显式传 `-O2`，而 O3 测试建议不传 `CMAKE_CXX_FLAGS`，让 CMake 自动处理。

### 实验 A：Noop Baseline
- 用空函数替换 `cache.get()`，测量 benchmark 框架自身扩展性
- 线程数：1 / 2 / 4 / 8 / 16

### 实验 B-C：多线程并发性能（R90W10）
- 线程数：1 / 2 / 4 / 8 / 16
- 读写比：90% GET + 10% PUT
- 两种命中率场景：
  - **Hit-heavy**：`preload_count == key_range` ≈ 100% 命中
  - **Miss-heavy**：`preload_count << key_range` ≈ ~10% 命中

### 实验 D：不同读写比例（固定 8 线程，miss-heavy）
- 读写比：R50W50 / R70W30 / R90W10 / R95W5 / R99W1

### 实验 E：向量检索性能
- 预填充 100,000 条 128 维向量
- 每线程执行 500 次 Top-10 向量检索
- 线程数：1 / 2 / 4 / 8

### 实验 F：分片数扩展性测试
- 固定 8 线程，R90W10
- F1 Hit-heavy：`preload_count == key_range`，测锁竞争和纯命中路径
- F2 Miss-heavy：`preload_count << key_range`，测真实缓存路径、miss、put 和 eviction
- 分片数：1 / 4 / 16 / 32 / 64 / 128 / 256

## O2 vs O3 对比分析

当前 O2 与 O3 数据均为 2026-06-18 的 `taskset -c 0-7` 同条件结果，可直接对比。整体看，O3 没有带来稳定收益，真实 KV workload 多数与 O2 持平或略低；主要瓶颈仍在同步、哈希、分片锁和内存访问，而不是编译优化等级。

本次同条件代表性结果：

| 场景 | 当前 O2 结果 |
|------|--------------|
| Noop 8T | 135.3M QPS |
| R90W10 hit-heavy 8T, 128 shards | 21.5M QPS |
| R90W10 miss-heavy 8T, 128 shards | 20.1M QPS |
| R99W1 miss-heavy 8T, 128 shards | 23.4M QPS |
| Vector Search 1T | 106 QPS |
| ShardScaling F1 256 shards | 24.2M QPS |
| ShardScaling F2 256 shards | 23.6M QPS |
| WAL ON 8T | O2: 14.1M QPS（较 OFF 下降 32.8%）；O3: 13.4M QPS（较 OFF 下降 28.3%） |

## 关键结论（2026-06-18 / taskset 0-7）

1. **Benchmark 框架不是瓶颈**：Noop 8 线程 O2/O3 都在 134M+ QPS，16 线程下降说明继续超出绑定 CPU 范围后主要受调度影响。
2. **128 分片下普通 KV 路径可到 20M+ QPS**：O2 R90W10 hit-heavy 8T 为 21.5M QPS，miss-heavy 8T 为 20.1M QPS；O3 对应为 21.0M / 20.2M。
3. **写比例仍主导尾延迟**：8T miss-heavy 下，R50W50 P99 为 8.22us，R99W1 P99 降到 2.25us。
4. **分片扩展有效**：hit-heavy 从 1 shard 的 1.5M QPS 增至 256 shards 的 24.2M QPS，P99 从 37.53us 降至 1.23us。
5. **向量检索仍是 memory bandwidth bound**：1→8 线程 QPS 基本保持 106→109，但 P99 从 10.4ms 升至 139.4ms。
6. **WAL 开销随并发上升**：O2 WAL ON 在 8T 为 14.1M QPS，较 OFF 下降 32.8%；O3 WAL ON 在 8T 为 13.4M QPS，较 OFF 下降 28.3%。16T 两者下降都约 40.4%，尾延迟增长更明显。
7. **WAL 的 P50 影响小，P99 影响大**：这说明 WAL 成本主要反映在高并发排队、批处理和后台持久化路径上，而不是每个请求的中位路径。
